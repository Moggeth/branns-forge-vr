## Pick: exactly which nodes changed
Input is the current `reference/assets/pick.glb` (the earlier mastery output).
1. **Removed `Embellish_Darkmetal_Spine`** (node 14, mesh 8, accessors 31–34, bufferViews 34–37, the binary tail from byte 253644). It had 96 triangles of `Steel_Blued`. 56 of those were the two 22 mm-thick arm-top plates (x 0.03→0.30, up to y 0.668) that read as a second blade or a metal ridge across the head.
2. **Added `Embellish_Darkmetal_Langets`** (`Steel_Blued`, 40 triangles, x ±0.009, y 0.375–0.545). These are the shaft langets from the removed node, generated by the same code with the same values. They sit on the shaft below the head, not across the top.
3. **Added `Embellish_Gold_ShardSettings`** (`Brass_Trim`, 720 triangles). These are gold bezel collars around the six existing arm-top resonance shards. Without the ridge, the inner shard pair would float about 4 mm above the measured head top (0.655 vs 0.651). The gems now read as set into the head, and you get more gem-and-gold detail with no metal ridge.
4. `StonewhisperPick.children`: removed index 14, appended 14 and 15. Nothing else in that node changed.

Unchanged and asserted by the builder (it throws if any of these change):
- Every other node is JSON-identical. That includes all sockets and empties (`Grip`, `HitCentre`, `ChargeGlow`, `PickTipLeft`, `PickTipRight`) with their translation, rotation and scale.
- All 5 materials, images, textures and samplers are JSON-identical.
- The embedded image bytes and the retained binary prefix are byte-identical. The pick has no external texture URIs; all 3 images are embedded bufferViews and are preserved.
- Bounds are identical: min (-0.32, -0.045, -0.0428), max (0.32, 0.718, 0.0428). So `prepareAsset` height normalisation, the origin, the axes and the collision tips do not move.
- The gems (`ResonanceCrystal`, `Embellish_Crystal_Crown`) and the twin-pick tips (`PickHead`) are untouched.

## Crossbow inspection (no change)
Measured against the reference `asset-pose.js`:
- In the cocked state the sled sits at y 0.535 (`.79 - .255`), matching its authored rest position. The sled spans y 0.479–0.557 and z 0.126–0.196.
- The bolt is at (0, 0.535, 0.179); its nock (y ≈ 0.539) sits inside the sled channel and its tip (y ≈ 1.061) lines up with `BoltSeat` z 0.179.
- When fired, the sled moves to 0.79 and the bolt hides at recoil ≥ 0.08.
- The gears, latch and trigger rotate around their own pivots in the render without visibly detaching.
- Materials look consistent in both states.

**Open issue for root, not changed:** the `LiveCord_*` string segments are static nodes. The asset has no morph targets, so the `Drawn` morph branch in `updateWeaponPresentation` has nothing to drive. In the top-down view the string converges at the same point whether cocked or fired, while the sled moves forward. If that matters, it should be fixed in runtime code (moving the `LiveCord` nodes with the sled) or with an authored `Drawn` morph. That would be a mechanism change rather than a small restoration, and nothing in the supplied client files drives `LiveCord`, so I left it.

## Limits
- The renders are the repo's own three.js copy on SwiftShader and RoomEnvironment lighting, not the game's own lighting or an HMD. Godot import and the actual `weapon_review.py` were not run here; that is for root.
- Without environment lighting, the metallic brass bezels render almost black (the first preview showed this). The game does set `scene.environment` (`game.js`, `orchard-presentation.js`), so the lit preview is the representative one.
- No HUD or reticle work, no edits outside this folder, no git.
