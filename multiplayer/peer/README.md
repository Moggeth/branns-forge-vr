# Browser hosted rooms

New rooms use eight numeric digits, preserving leading zeros. Join accepts spaces
or a hyphen between digits. Codes are short invitations, not authentication;
reconnect credentials remain separate 256-bit secrets. Creation checks collisions
and join attempts are rate limited across sockets per source IP.

`server.mjs` is a small signaling process for rooms of up to 32 browsers. The first browser is the host and owns simulation. The service routes WebRTC offers, answers, and ICE candidates, appoints a new host after explicit acceptance, and never receives game commands, snapshots, or checkpoints. Browsers connect to the host using reliable WebRTC data channels. Each channel frame carries a signaling epoch; stale frames are discarded after ownership changes.

Start from `multiplayer/` with `node peer/server.mjs`. Set `PEER_ORIGINS` to a comma-separated exact list of browser origins (for example, `https://forge.example.com`). It defaults to local Vite origins for development. Set `PEER_HOST` and `PEER_PORT` for the tunnel listener; defaults are `127.0.0.1:8789`. Expose `/peer/ws` through an HTTPS tunnel so remote browsers use `wss://`. `GET /peer/health` returns room/peer counts and process uptime. `GET /peer/config` returns public STUN URLs and whether a TURN relay is configured. Start and stop the process through the usual Node process manager or SIGINT/SIGTERM; shutdown closes sockets. Logs are timestamped JSON lines in `peer/logs/server.jsonl` by default, with room and peer IDs only. They are ignored by Git. `node peer/test.mjs` runs a local signaling contract check. `PEER_LOG_PATH` can redirect the log.

Environment controls: `PEER_MAX_ROOMS` (100), `PEER_MAX_PEERS` (default and hard cap 32 human players), `PEER_ROOM_IDLE_MS` (30 minutes), `PEER_ROOM_MAX_AGE_MS` (8 hours), `PEER_SHUTDOWN_IDLE_MS` (optional process shutdown after empty time), `PEER_DISCONNECT_GRACE_MS` (15 seconds), `PEER_CONTINUE_OFFER_MS` (2 minutes), `PEER_STUN_URLS` (comma-separated), and optional `PEER_TURN_URL` plus `PEER_TURN_SECRET`. TURN uses short-lived coturn shared-secret REST credentials in each welcome and `/peer/config`, with expiry controlled by `PEER_TURN_TTL_SEC` (maximum one hour, default ten minutes). Configure coturn with the same shared secret. A STUN server alone cannot connect every pair of networks; when relay is unconfigured, the UI should explain that some players may be unable to connect. The service does not claim guaranteed connectivity.

`browser.js` exports `PeerRoomConnection extends EventTarget`. Construct with `{url}` and call `connect({room:'',name,role:'hero'|'god',desktop:true,secret:''})`; empty `room` creates a room. A successful `welcome` event provides `{room,peerId,secret,hostId,epoch,peers,isHost,relayConfigured}`. Keep `secret` in memory or session storage only. A room invite may include the room code in a URL; **never** put `secret` in a URL or log. To reconnect the same peer, call `connect` with its room and secret. Public properties include `room`, `peerId`, `hostId`, `epoch`, `isHost`, `roster` (Map), `checkpoint`, and `checkpointRevision`. The `identity` getter exposes room, peerId, role, and secret.

Events used by a game controller: `roster` `{peers,epoch}`, `peer_joined` peer object, `peer_left` `{peerId}`, `peer_connected` `{peerId}` when its WebRTC channel opens, `peer_disconnected`, `message` `{from,data}`, `checkpoint` `{from,state,revision,epoch}`, `owner_lost` `{epoch}`, `continue_world_offer` `{epoch,revision,graceful,checkpoint}`, `host_changed` `{hostId,previousHostId,epoch,isHost}`, `host_promoted` `{epoch,checkpoint,revision,peers}` only on the newly appointed host, plus `status` and `error`. Host methods are `send(peerId,data)`, `broadcast(data)` (number sent), and `setCheckpoint(state,revision)`. Guests may `send(hostId,data)` only. `send` returns false if the channel is not open or its send queue is full. A new `peer_connected` event is the point to send the latest full state. `setCheckpoint` delivers the checkpoint over WebRTC in 12 KB chunks. Each receiving peer stores it, emits `checkpoint`, then tells signaling only the revision it holds.

If the host disconnects, `owner_lost` tells every client to pause simulation. Signaling waits for a brief reconnect, then offers the highest revision checkpoint held by an online desktop peer. The UI must show an explicit **Continue world** choice and call `continueWorld()` only after acceptance; `declineWorld()` moves to another eligible peer. An offer lasts two minutes by default; `continue_offer_expired` tells the UI to hide its stale prompt. If no candidate accepts, `world_waiting` indicates that the room is paused. A desktop peer with a checkpoint can call `retryWorld()` to request a new offer. When accepted, the service increments the epoch and broadcasts `host_changed`; the new owner receives `host_promoted` with its local checkpoint and roster. `transferHost(peerId)` starts the same acceptance flow while the old host is still online. A disconnected owner that reconnects after a new epoch is a normal guest, never an automatic owner. This is a single live room process: server restart ends all rooms; game persistence, if desired, belongs to the host application.

The service rejects origins outside the configured exact list, limits room creation per IP, message rate and size, enforces room capacity, removes idle rooms, and closes dead sockets using heartbeats. Treat every game command as untrusted in the host simulation and use the authenticated `message.detail.from` sender ID; never accept a sender ID from packet content.


### Recovery checkpoint transport

Desktop recovery checkpoints keep their 2 Hz cadence (other devices receive them every 10 seconds). New clients negotiate `checkpoint_codec` version 1 on the authenticated game edge. Checkpoints then use an independent `checkpoint_delta` stream built on the bounded, hashed JSON delta codec. They are never quantized: positions, simulation clocks, inventories, unknown forward-compatible fields, and battle state retain their exact JSON values. A full keyframe is sent for a new peer, missing/corrupt base, failed send, stream/host change, and periodically every 20 recovery publications. Legacy guests/hosts keep full `checkpoint` envelopes. The last verified checkpoint remains usable while a delta resynchronizes; live display snapshots cannot overwrite this recovery base.

Room capacity is 32 human identities; simulation bots consume no room seats. Host signaling and relay budgets scale with actual online star edges (up to 31), while guest budgets stay at one edge. Cloud room sockets remain bounded at 32 joined plus 8 pending/reconnect attempts, and the shared-IP join allowance is 64/minute. Public listing joinability respects the five-second reserved-seat reconnect grace.

`node tests/network-capacity.mjs` and `node tests/checkpoint-delta.mjs` verify capacity/routing budgets and exact recovery. `node tests/32-player-transport.mjs` runs a manual 32-page Chromium transport test against local Vite and the cloud emulator, including active battle bots and host transfer. Set `FORCE_RELAY=1` to force the WebSocket fallback. This lightweight harness does not render the game and is not a phone/headset FPS guarantee. Disable development hot reload during concurrent source edits so it cannot restart acceptance sessions mid-measurement.

### Mixed-version rollout

The current browser advertises `simCapacity: 32` when creating, joining or reconnecting. Missing or invalid metadata means the legacy eight-player simulation, including records persisted before a coordinator upgrade. Both cloud and local signaling use the lowest capacity of all retained room members; upgrading only the host does not expose older recovery peers to an unloadable world. Old rooms stay at eight until all retained old members refresh or depart. A pre-update client trying to join a new 32-capable room receives `client_update_required` with a refresh instruction. Reconnects preserve identity/checkpoint revision and can upgrade capacity without evicting anyone; an old reconnect cannot downgrade a room already above eight. Host-transfer candidates must support the entire retained roster. Public listings use this negotiated capacity and preserve the reconnect-seat grace period.

Run `node tests/room-capacity.mjs` and `node peer/capacity-test.mjs` for mixed-version admission, refresh, listing, reserved-seat and migration regression checks. Raw signaling clients in integration harnesses must advertise their actual capability explicitly; omitting it deliberately exercises legacy capacity.

The negotiated `maxPeers` is included in welcome, membership and host-change messages and retained by `PeerRoomConnection`. Missing metadata from an old coordinator defaults to eight. Battle start/reset is denied with `client_update_required` while that limit is below32; stopping remains available, and local solo bypasses this multiplayer compatibility gate. `WorldSession.battleCompatible` exposes the same rule to presentation code. Membership changes update this state before their events reach the HUD.
