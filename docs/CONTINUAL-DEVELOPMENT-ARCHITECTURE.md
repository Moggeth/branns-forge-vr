# Continual development architecture

Status: source review and offline preflight, 26 September 2026. This is a direction for expanding Brann's creative range while preserving a running game, not a claim that arbitrary new engine code can be loaded during play.

## What works today

The running Godot game polls `/api/vr/state`, passes `liveWorkshop` into `living_runtime.gd`, and reconciles requested package versions. The service's `LivingWorkshop` stores immutable JSON versions, validates names, geometry, components, links, rules, scope, budgets, and exact dependencies, and exposes a catalog to Brann. `publish_living_package`, `publish_living_batch`, `restore_living_version`, and `inspect_living_workshop` are actual agent tools. The service distinguishes a saved `published` request from the native client's `applied`, `deferred`, or `rejected` acknowledgement.

Godot loads registered native primitives from `living_components.gd` and validates their configuration against its pinned `living_capabilities.json`. `living_runtime.gd` validates again, builds hidden staging containers, waits one frame, then swaps active scenes without yielding. It preserves a previous version on a rejected build or failed activation. Held objects and occupied regions defer replacement or removal. A batch shares a transaction id, but the service's save transaction and native scene activation are different boundaries: native groups can apply independently; the batch is not a global all-or-nothing world swap. Exact dependency versions can delay a package until its provider is active.

The manifest can add package-owned items, regions, rules, and devices from existing shapes and components: grips and returning projectiles, material reactions, emitters/sensors, reservoirs and links, creatures, local fields, climb/grapple/portal, objectives, maker/transformer/trigger, and bounded player embodiment. Rules compose registered actions such as heat, power, move, color, and objective. These are the supported live extensions. Detailed GLB commissions and their bounded existing ability path also arrive while running, but they are a separate path, not proof that a new Living Workshop primitive can be installed live.

Service history and provenance survive in `service/data/living-workshop.json`. Native package state is snapshotted to `user://living_world.json` periodically and on exit, with up to 64 version-state entries. A game restart is needed to load changed GDScript, native component implementations, the pinned catalog, engine assets, or main-scene integration. The game also needs one initial restart to load this foundation if an older process predates it. No package executes incoming scripts, gains file access, or mutates arbitrary baseline nodes.

## Capability growth boundary

| Change Brann requests | Current delivery path | Restart? |
|---|---|---|
| New combination of known components, rules, or shapes | Publish a new validated package version and wait for native `applied` | No, after foundation is running |
| Tune an existing package or restore an old version | Publish next immutable version or request rollback | No, subject to safe deferral |
| A new GLB with a supported bounded legacy ability | Existing commission pipeline | No for delivery; generated ability remains constrained by its own host |
| New physics behavior, input gesture, renderer, enemy AI, component type, or action op | Developer adds native primitive, schema, tests, and migration support | Yes |
| Global rewrite of existing scenery, game progression, or unrestricted executable logic | New explicit engine/product design and trust boundary | Not supported by package v1 |

The right long-term split is a small stable native interpreter plus an expanding declarative vocabulary. Treat capability version as a compatibility contract, not simply a marketing number: each new primitive needs a native handler, service schema/catalog, pinned native schema, old-version behavior, and representative in-engine checks. Existing `capabilityVersion:1` is global while individual component versions are currently `1`; there is no negotiated client capability set yet. Preserve historical version-1 semantics when adding version 2 so rollback remains meaningful.

## Next implementation sequence

1. **Make compatibility observable before publishing.** Add a native startup report of engine build/capability version and catalog digest, with service comparison and a clear incompatible status. Presently catalog equality is tested in source, but the service cannot prove which build a running client loaded. Refuse a publish when the connected client cannot interpret it, or label it pending until that client is updated. Keep `published` and `applied` separate.
2. **Define a versioned capability descriptor.** Keep package schema, primitive versions, config limits, action semantics, state serialization format, and migration policy explicit. Generate both service and native validation data from one reviewed descriptor, but do not send the native trust policy inside user packages. Add old-version fixtures before extending the vocabulary. Reject unknown fields and unavailable primitives at both boundaries.
3. **Add a package preflight and deployment view.** Check candidate packages, exact dependency closure, active-world budgets, and target-client capability compatibility before the agent offers them. Show per-package pending/deferred/rejected/applied status, native reason, generation, and last matching client session. Acknowledgement should follow a verified scene outcome; a service save is not delivery.
4. **Expand primitives in narrow vertical slices.** For each concrete player request, implement one reusable native primitive with bounded configuration and observability. Add service validation, native validation, representative headset or desktop interaction checks, and a demo package. Prefer object-local effects over new global hooks. When a new engine build lands, existing v1 packages must still load unchanged.
5. **Harden state and batch semantics.** Specify per-component state migrations and what happens when an older version is restored. Add a health check that reconciles desired and applied generations after reconnect. If multi-package atomic scene swap is required, implement explicit dependency-order staging and rollback across the whole group; the current batch save alone does not provide it. Preserve held/occupied deferrals.
6. **Only then consider a richer sandbox.** If declarative rules prove too limited, design a separate reviewed interpreter with deterministic instruction, memory, event, and time budgets and no OS/network/file access. This would be a new trust boundary requiring engine-side enforcement. Do not treat the existing bounded legacy JavaScript commission host as authority to run package scripts in Godot.

## Offline preflight added here

`node service/living-capability-audit.cjs` reads the shipped demo package list, validates each package through the service's authoritative `validatePackage`, and checks that the native pinned catalog equals the service catalog. It writes no state and makes no network request. Pass a JSON path to audit another array of versions. An object shaped `{ "packages": [...], "desired": [{"id":"...","version":1}] }` also checks one proposed active set for exact dependencies, cycles, duplicate active ids, and aggregate package/entity/body budgets. Use it before publishing, then inspect the native acknowledgement after publication. This static preflight does not execute the GDScript validator, construct a scene, prove physical playability, or know the capability set of an already running game process.

## Evidence and measured work

Source inspected: `service/living-workshop.js`, `service/forge.js`, `service/server.js`, `godot/living_runtime.gd`, `godot/living_component_schema.gd`, `godot/living_components.gd`, `godot/main.gd`, existing Living Workshop contract/service/component docs, and verification guidance. The focused and existing Living Workshop tests pass (17/17, 0.57 s process wall time); the shipped demo audit passes (12 versions, 0.10 s process wall time). No live service or game was restarted, no paid generation was used, and no Git repository was initialized.

Tool wall times measured during this review: initial project discovery 0.5 s; batched instructions/source reads 1.0 s; targeted symbol/document reads 0.9 s; detailed service/native reads 1.1 s; demo inventory 0.4 s; first audit test 0.5 s (failed because its fixture changed an id without updating package scope); corrected focused test 0.5 s (passed); final test, audit, and file check batched 1.0 s. The fixture lesson is to mutate only the capability under test; package id and scope target must remain consistent, or the service rightly rejects scope first. These measurements cover tool calls, not drafting time, and should not be summed as elapsed task time.
