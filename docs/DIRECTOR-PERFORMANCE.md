# Director performance investigation — 2026-09-26

The current same-PC Director camera is a 1024×576 `SubViewport` sharing the adventurer's `World3D`, with 2× MSAA. While the browser is connected, Godot requests one render at most every 0.20 seconds. It waits for `frame_post_draw`, reads RGBA from the GPU asynchronously when supported, constructs an `Image`, encodes JPEG at quality 0.78, and posts it over loopback HTTP. The service stores the latest JPEG in memory; the browser fetches and displays it. The game polls commands and posts state roughly every 0.15 seconds, while the visible browser polls state every 220 ms. The viewport is disabled without a viewer.

At five frames per second, a raw 1024×576 RGBA image is 2,359,296 bytes; readback traffic is at most **11.25 MiB/s** before JPEG. The recorded first desktop frame was **57,554 JPEG bytes** (about 0.29 MB/s at five frames/s). These data volumes are modest. The more serious cost is per-frame latency: the prior desktop frame check recorded **5.4 ms** for callback-side image conversion plus JPEG encoding using async readback. Earlier synchronous `get_image()` capture cost about **20 ms total** with a **16–19 ms readback stall**. The `DIRECTOR_FRAME` counter does not include the second camera's GPU render time, GPU transfer latency before the async callback, HTTP, or browser presentation. Its `read_avg_ms=0.0` on the async path means that synchronous fallback read time was zero, not that GPU readback is free.

The headset frame budget is **11.11 ms at 90 Hz** and **8.33 ms at 120 Hz**. If 5.4 ms of encoding lands on a headset frame, it consumes roughly 49% or 65% of those budgets before the game and stereo scene render. The second camera adds an independent scene render on capture frames. Its actual GPU cost is not instrumented, so the likely headset risk is a periodic frame spike from the additional render and main-thread JPEG work. It would be incorrect to infer smooth 90/120 Hz VR from the desktop 120 fps logs.

## Native monitor prototype

`node scripts/check-director-performance.cjs --native-window` launches a separate Godot process for about five seconds. It creates a 144-box scene, samples the primary window for two seconds, adds a second native `Window` with a separate `Camera3D` and **the same `World3D`**, then samples two more seconds. It reads one image from the second window after sampling to verify the viewport has real pixels. It does not load the match, use the live service, modify saves, or stop the running game. The source audit alone is `node scripts/check-director-performance.cjs`.

On this RTX 3080 Ti desktop, one isolated run returned a 640×360 second-window image with two sampled colors, shared-world identity `true`, primary-only 242 frames / 8.24 ms mean / 8.34 ms p95, and two-window 241 frames / 8.34 ms mean / 8.33 ms p95. These numbers are limited by the 120 Hz presentation cadence and a tiny synthetic scene; they prove API feasibility, **not** that the real Pinewood scene or VR can afford a continuously rendering second window. A separate run measured 8.29 and 8.38 ms means, also capped by presentation.

## Implemented local direction

The same-PC Director now renders a tactical camera into a native Godot window and handles controls in Godot. Its throttled `SubViewport` shares the adventurer's `World3D` and presents the texture directly. This removes GPU-to-CPU readback, JPEG compression, loopback image upload, browser image decoding, and their callback spikes. State and combat authority stay in the existing Godot simulation. The default is 60 tactical frames/s at 75% render scale, with 30 fps and 50% options for headset comfort. The browser route remains an optional fallback.

The complete Pinewood desktop rehearsal with the local Director window measured 120 engine FPS, 8.33 ms mean, 9.33 ms p95, and 9.56 ms p99 over 360 frames. This verifies a smooth desktop session on this PC, not headset comfort or a 120 fps projector render. The Director camera may still consume meaningful GPU time in stereo VR. Use `scripts/check-director-local.ps1 -DesktopVisual` to repeat the desktop checks and inspect `DIRECTOR_PERF` in `logs/game-*.log` during a live session.

For the headset performance comparison, instrument frame time and GPU time for: no Director, Director with viewer disconnected, current five-frame viewer, native window with throttled camera, and native window with the camera disabled. Collect at least median, p95 and p99 frame time plus missed frames during movement and combat. Use the same Pinewood path and SteamVR runtime. This isolates the second render pass from transfer/encoding. A headset result has not yet been obtained: SteamVR did not expose a compositor during this development session, and OpenXR `xrCreateInstance` failed with error -2.

## Timing and recovery notes

Measured wall-clock steps for this investigation (seconds, tool wall time): project discovery 0.4; AGENTS/state inspection 0.5; source/architecture reads 1.3 + 0.5 + 0.5; initial native probe parse failure 1.4; first executable probe with camera-order errors 5.5; corrected native probe 5.7; source audit plus native probe 5.5; pixel-check and final assertion probes 5.6 + 5.6. The failed parse came from treating `SceneTree._process` like `Node._process`; it must return `bool`, and SceneTree has no `set_process`. The camera errors came from calling `look_at()` before adding the camera to the tree. The probe now adds cameras first and exits itself after both sample windows. Do not add `--quit-after 400`: it ends the run before the second two-second sample completes.

Further recovery lessons: use `node scripts/check-director.cjs` for the existing offline match assertions; running its GDScript directly without the script's `--director-check` argument leaves the Director uninitialized and can stall. A headless Godot run cannot verify the rendered second window; use `godot/director_local_visual_check.gd` in graphical mode. Check `tactical_viewport.world_3d` to establish shared-world identity; the outer `Window.world_3d` is not the tactical camera's viewport. Do not run OpenXR VR checks without SteamVR's compositor ready: the runtime returned `xrCreateInstance` error -2 and the attempted probe hung. For unattended checks use `--xr-mode off`; for real headset evidence, start SteamVR with headset/controllers ready and then run the VR launcher. These failure paths were isolated and stopped without touching other Godot or SteamVR processes.
