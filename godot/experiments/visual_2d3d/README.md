# Orchard Brook Godot compiler

`world_builder.gd` turns a saved `world_spec` v1 JSON plan into an isolated Godot scene. It never loads `main.tscn`, player progress, the forge service, or XR. It uses the existing `res://assets/orchard/*.glb` library, with the same vertex-colour repair and MultiMesh batching as the playable orchard. The compiler makes 1 m terrain triangles, a recessed stream, path surface, colliding stone bridge, sparse seeded foliage and object footprints. `run_world.gd` validates the plan, raycasts the physical bridge and spawn ground, saves `world.tscn`, and renders the five fixed benchmark views.

From the repository root:

```powershell
& godot/experiments/visual_2d3d/Run-World.ps1 -Spec godot/experiments/visual_2d3d/sample_world_spec.json -Out godot/experiments/visual_2d3d/sample_output
& godot/experiments/visual_2d3d/Run-World.ps1 -Spec experiments/visual-2d3d-20260928/variants/D/world_spec.json -Out godot/experiments/visual_2d3d/d_smoke
```

Use `-Headless -CheckOnly` for fast schema and route validation. Use `-Headless` without `-CheckOnly` to compile the scene without PNG readback; its metrics say `unavailable_headless_display`. Normal windowed execution renders via the local Vulkan desktop renderer and exits automatically. Output paths are local, generated experiment artifacts. Open an output `world.tscn` from inside the Godot project to inspect it, or copy it under the project if the output was elsewhere. `metrics.json` holds validation, node/triangle counts and measured build/render times. A console run takes longer than the in-engine times because engine startup is included.

The bridge's long axis is local Z; `yaw_rad=0` runs north/south. Stream and path arrays use Godot X/Z metres with north at negative Z. Trees are deliberately placed from saved polygons and a seed; `tree_density` is a 0–1 control and each region is capped at 240 candidate placements for a compact comparison. Regions currently affect foliage placement, while their `surface` labels are preserved in the JSON but terrain material remains common across variants. Explicit object `position_xyz` is respected; `center_xyz` remains a compatible alias. `terrain.base_y` is preferred; earlier `base_height_m` remains an alias.

Optional `terrain.gaussian_coefficient` controls hill falloff: each contribution is `amplitude_m * exp(-coefficient * distance² / radius_m²)`. The default `0.5` preserves early specs; Opus A and C use `1.0`. Optional `terrain.stream_carve` selects `legacy` (default 1.8 m smooth bank), `none` (C's negative hills already carve the channel), or `{"kind":"valley_channel","valley_depth_m":1.0,"valley_radius_m":12.0,"channel_depth_m":1.9,"channel_smoothstep_m":[1.2,4.5],"water_below_ground_m":1.35}` (A's declared ravine). A's water follows uncarved valley ground minus the configured offset. `none` uses `stream.c_water_y` when present. This affects the saved mesh, grade checks, and water ribbon from the same specification.

Hybrid specs may set `crossing.asset_glb` to an imported `res://assets/.../*.glb` and `landmark.asset_glb` to another imported asset. The bridge visual attaches at the crossing centre and follows `crossing.yaw_rad`; optional `asset_scale`, `asset_y_offset_m` and `asset_yaw_offset_rad` align the authored model. When present, the procedural bridge visual is replaced by the GLB while a width/length matched invisible deck collider remains. A dedicated physics raycast verifies that fallback independently of any `-colonly` shapes that Godot may import from the model. The landmark defaults to the goal's ground height, or uses `landmark.position_xyz`; optional `yaw_rad`, `scale`, `asset_y_offset_m`, `collision_radius_m`, and `collision_height_m` tune it. A small fallback collider and dedicated raycast verify its physical presence. Asset paths outside `res://assets/`, traversal paths, backslashes, missing imports and non-GLB resources fail validation. Import new GLBs in the project editor before running this script; the runner does not modify asset import settings. Match the authored bridge deck surface to the fallback deck top at crossing base height plus 0.63 m before claiming a usable walkable surface.

The `hybrid_fixture_world_spec.json` demonstrates this path with the existing orchard `path_straight.glb` enlarged across the stream and `wall_corner_broken.glb` at the goal. Run `Run-World.ps1 -Spec godot/experiments/visual_2d3d/hybrid_fixture_world_spec.json -Out godot/experiments/visual_2d3d/e_fixture` from the repository root. Its five captures and metrics prove import, transform, scene save and collision; the placeholder art is not the specialist E bridge or landmark.

Hard checks cover required fields, bounded rectangular dimensions, spawn/goal path endpoints, stream/bridge widths, bridge centre and orientation, route contact with the bridge, sub-metre route grade sampling away from the bridge, stream encounters away from the crossing, object path obstruction, and physical raycasts on the bridge/spawn. These are useful gates, not a navmesh or a verified player traversal. Water is non-fordable by a recessed bank and route rule; there is no player drowning script in this isolated test. The physical deck is collidable. In-headset comfort, VR frame rate and stereo appearance remain unmeasured.

`path_straight`, `path_curve30` and `path_curve30_left` are walkable surface decals. They can lie on the required route and do not create the generic cylindrical object footprint. Trees, rocks, walls and other props retain route obstruction checks and physical footprints. This distinction allows Opus A's 16 authored path pieces while a rock placed at one of those positions still fails validation.

The first smoke render revealed that the procedural faces were culled and Orchard GLBs imported without their intended vertex colours. Face winding and `orchard_finish.gd` application fixed those failures. A first D check rejected a yaw convention mismatch; the deck is now along Godot's forward Z axis and D passes. The first batched overhead capture hid distant trees because the live orchard adapter sets visibility range to 90 m; the evaluation scene removes that range so all variants remain visible from the fixed 85 m camera. If these symptoms recur, inspect `overhead.png` before adjusting colours or GLB files. Diagnostic metrics and five PNGs are enough to compare changes without rerunning image generation or specialist asset construction.

The sample is a compiler fixture, not one of the five evaluated pipelines. `a_smoke/`, `b_smoke/`, `c_smoke/`, and `d_smoke/` are common-renderer builds. A/C used local flagged spec copies while those fields were being added upstream. All four built and rendered with physical bridge/spawn raycasts true; their measured in-engine route grades were A 0.13, B 0.02, C 0.11 and D 0.02. These are desktop Vulkan captures, not measured VR performance. The common compiler does not realize optional `c_procedural.beacon` or A's specialist beacon geometry, so A/C landmark frames should not be presented as complete specialist scenes. Their authored GLB path pieces also show rectangular overlays on the shared procedural path. This is visible evidence of a representation gap, not a spec validation failure.

`bounds_m:[width,depth]` supports centred rectangular worlds from 20 to 256 m per side. The terrain grid uses approximately 1 m cells across each dimension, and seeded foliage samples the full bounds with candidate count scaled by area. The 80 × 80 m case uses the same grid, placement range and fixed benchmark cameras as before. Expanded worlds keep the crossing camera anchored to the bridge, move approach and goal cameras with the spawn/goal, and raise the overhead camera by the larger dimension's scale; their `camera_mode` and exact poses are in `metrics.json`. Expanded worlds also sample physical route collision at roughly 2 m intervals and require ground/deck hits, no blocking props and a maximum sampled height step below 0.8 m. These checks give useful offline traversal evidence, but they are not a real player or headset walk-through.

Create and render the saved 160 m fixture from the repository root:

```powershell
python godot/experiments/visual_2d3d/make_scale_fixture.py --out godot/experiments/visual_2d3d/scale_160_world_spec.json --width 160 --depth 160
& godot/experiments/visual_2d3d/Run-World.ps1 -Spec godot/experiments/visual_2d3d/scale_160_world_spec.json -Out godot/experiments/visual_2d3d/scale_160_output
```

The 80 m regression compiled and rendered in 1.974 s desktop wall time (12,800 terrain triangles, 69 seeded foliage positions, 226 nodes; engine build 0.23 s, render 0.14 s). The 160 × 160 m fixture took 2.604 s on the final route-checked run (51,200 terrain triangles, 316 seeded foliage positions, 831 nodes; engine build 0.705 s, render 0.155 s). It passed 86 physical route samples with five bridge-deck hits, zero missing/blocking hits, and a 0.435 m maximum sampled height step. A 160 × 120 m rectangular fixture also compiled and rendered, and its overhead shows the correct aspect ratio. These are short desktop build/readback times, not sustained frame rates or VR measurements. The larger fixture scales the same simple layout and assets; it tests compiler cost and route coherence, not a richer art-directed 160 m world.
